# Security / privacy / governance risk memo (observed 2026-07-21, public sources only)

NOT LEGAL ADVICE. Applicability depends on jurisdiction, the exact account agreement accepted, whether the operator processes only their own data, and whether the bridge is used personally or as a service.

## Legal / access risk

Observed code describes itself as "simulating the CareLink mobile app's OAuth2 authentication and API calls" (package.json) and does materially emulate the app: `src/login.ts` sends discovery version `android/3.6`, a mobile-browser user agent, adopts Medtronic's published Auth0 client ID/audience/registered redirect URI, and uses PKCE. Its browser strategy uses Chrome DevTools Protocol to capture an authorization code from redirects to `com.medtronic.carelink://`; its terminal fallback instructs the user to copy the code-bearing redirect URL from DevTools. The client then calls undocumented patient/care-partner endpoints. These are observed technical facts, not a legal conclusion.

This creates substantial contract/account-continuity risk because access is outside a documented public developer program and the product terms reserve termination for nonconforming or disruptive use. It may also implicate contract, anti-circumvention, computer-access, copyright, or interoperability rules differently by jurisdiction. Whether it violates any term or law requires qualified legal review. No official public CareLink Personal API policy or developer-access program was found in this review; absence is not proof none exists.

Guardrails: keep the project personal, non-commercial, single-account, user-authorized, and read-only toward CareLink; never advertise affiliation or endorsement; never provide a hosted credential-collection service or multi-tenant account proxy without legal/privacy/security review; do not reuse one user's credentials/tokens for another; preserve user-initiated CAPTCHA/MFA rather than defeating it; stop on account suspension, explicit denial, or a provider request; record the exact locale terms/version accepted; and periodically re-review official terms because both official terms pages reserve changes.

## Operational / API boundaries

No authoritative public CareLink Personal rate-limit specification was found. The repository's issue #12 calls limits "real but undocumented" and recommends watching for HTTP 429; the systemd unit limits restart loops to 5 starts/300 seconds with 30-second restart delay. Therefore numeric limits must not be invented. The code defaults to one fetch per five minutes, caps a fetch at 30 requests, and performs up to three retries with 2/4/8-second delays, but retry behavior has no jitter and can multiply requests during failure.

Public history establishes instability, not contractual permission: EU endpoint/authentication changes broke clients in 2020 (mddub/minimed-connect-to-nightscout#18); US authentication/IP behavior and device/role differences produced 404/stale-data failures (nightscout/minimed-connect-to-nightscout#11); reCAPTCHA broke unattended login and contributors urged no more than five-minute polling plus jitter to avoid herd effects (nightscout/minimed-connect-to-nightscout#47). These are community reports, not authoritative Medtronic policies. Current fork research/status is tracked at https://github.com/NovaLux12/carelink-bridge/issues/12 and explicitly notes real-data validation is deferred until November 2026.

Engineering guardrails: retain a minimum five-minute interval unless authoritative permission says otherwise; never synchronize all installations at the exact boundary — add bounded jitter; honor 429 and `Retry-After` if received; use exponential backoff with a ceiling and circuit breaker; avoid retries for most 4xx responses; retain per-fetch and per-time-window request budgets; ensure restarts cannot bypass budgets; do not probe version ranges or endpoint inventories in production; treat CAPTCHA, MFA, 401/403, and changed discovery config as stop/re-auth signals rather than obstacles to bypass; and make endpoint changes from observed official app/config behavior only, at low rate, with the user's own account and redacted records.

## Privacy / security posture of this app

Positive observed controls: SECURITY.md identifies CareLink tokens, Nightscout write secrets, and pump/CGM medical data as protected assets; provides private GitHub Advisory reporting; warns the software is unaffiliated, unapproved, and unsuitable as the sole basis for medical decisions; removes fork-specific proxy routing; minimizes runtime dependencies; documents Dependabot/branch protection. `.env` and `logindata.json` are gitignored. Deployment recommends `.env` mode 0600 and supplies systemd defense in depth (`NoNewPrivileges`, `PrivateTmp`, `ProtectSystem=strict`, `ProtectHome=read-only`, no inbound listener, journal logging, bounded restart). HTTPS is used for CareLink and documented Nightscout configuration.

High credential gap: `src/login.ts` and `src/carelink/token.ts` write `logindata.json` using `fs.writeFileSync` with no explicit mode. On a normal umask 022, a newly created file is typically 0644 [INFERENCE], readable by other local users. It contains `access_token`, `refresh_token`, `client_id`, token URL, audience and scope, and SECURITY.md characterizes the tokens as full account access. Refresh writes also replace the file non-atomically. Required consequence: create/write atomically with mode 0600, tighten existing files on load, verify ownership, refuse symlinks/untrusted paths, and document rotation/revocation/re-login after suspected exposure. Also set umask 077 as defense in depth and ensure backups exclude or encrypt this file.

High medical-data logging gap: `src/nightscout/upload.ts` logs the full JSON upload entries when verbose mode is enabled; the systemd unit sends stdout/stderr to journald. Thus pump/CGM data can persist in the journal and be copied into support reports or centralized logging. Required consequence: never log medical payloads; log only counts, destination origin/path, time range, and opaque correlation IDs. Redact usernames, patient IDs, serials, token claims, authorization URLs/codes, cookies, headers, raw response bodies, and Nightscout secrets. Establish bounded journal retention and a safe support-bundle/redaction process.

Other consequences: `.env` deliberately stores the primary CareLink password and Nightscout secret, so prefer a dedicated OS user, 0600 ownership, encrypted host/storage/backups, no shell history or process-list exposure, and documented credential rotation. `API_SECRET` is SHA-1 hashed for the legacy Nightscout `api-secret` protocol; hashing does not make a weak/reused secret safe, so require a long unique random Nightscout secret and TLS. Do not add proxies/Tor casually: the README permits standard proxy variables, which can expose destination metadata and — if TLS trust is altered — credentials/health data. Pinning or allowlisting endpoint origins before sending bearer tokens is advisable; currently some BLE endpoints are supplied by CareLink configuration and then called.

## Medical-safety risk

The official CareLink terms say the site does not render medical advice, must not substitute for professional assessment, and should not be relied on for clinical decisions. This bridge adds transformation, clock-offset inference, filtering, retries, stale copies and a second database. Public issue history shows endpoint changes, stale timestamps, device/role variations, concurrent-login invalidation and CAPTCHA changes. SECURITY.md itself warns compromise or bad writes could pollute Nightscout and affect insulin decisions.

Guardrails: remain strictly open-loop/read-only — no dosing, pump control, alarm replacement, or automatic clinical action; label data as delayed/unofficial and show source timestamp, last successful fetch, and stale/error state; fail visibly rather than presenting old data as current; preserve provenance and deduplicate; test timestamp/DST/travel boundaries; compare first real deployment against official displays without publishing identifiable payloads; maintain an independent glucose-monitoring/emergency path; tell users to follow device labeling and clinician advice. No health, alarm, or availability promise should exceed what was actually validated.

## Public disclosures (must NOT conflate)

Medtronic's CareLink Network bulletin and NVD CVE-2025-12996 describe sensitive data in server logs, but they are NOT applicable to this app's target. The vendor explicitly says CareLink Network is for cardiovascular products and that CareLink Personal/Clinic are different diabetes systems; no diabetes products are impacted: https://www.medtronic.com/en-us/e/product-security/security-bulletins/carelink-network-vulnerabilities.html and https://nvd.nist.gov/vuln/detail/cve-2025-12996. This should not be cited as evidence of a CareLink Personal vulnerability. It is at most a general reminder that logs are a sensitive-data boundary.

## Responsible future-investigation boundary

Permitted: public documentation/source/package review; low-rate unauthenticated GETs to clearly public configuration resources; own-account, user-consented functional validation; mocked fixtures; and private disclosure of discovered vulnerabilities. Prohibited: CAPTCHA/MFA bypass or solving services, credential stuffing, enumeration, multi-account testing, access to other patients, harvesting tokens/cookies/HAR files, shared-cloud IP evasion, undocumented high-volume scanning, destructive requests, fuzzing production, circumventing suspension, publishing working secrets/identifiers, or claiming authorization from public reachability. Never ask issue reporters for raw HAR/logindata/payloads; provide field-level redaction instructions and use the repository's private advisory channel for security reports.

## Open questions

- Which exact CareLink Personal terms/account agreement does each EU/US locale present at registration/login, and do they expressly address automated clients, reverse engineering, credential sharing, third-party export, or API access?
- Does Medtronic offer a documented patient export, approved partner API, consent flow, or written permission route suitable for Nightscout?
- What scopes and actual privileges do the issued Auth0 tokens carry? SECURITY.md calls them full-account access, but scope/authorization should be verified from public config or the operator's own decoded token without publishing it.
- How should a Nightscout operator document controller/processor roles, lawful basis, DPIA/security assessment, retention, deletion, incident response, minors/guardians, and international transfers in their jurisdiction?
- What server-side throttling/`Retry-After` behavior is observed during normal own-account operation? Do not probe deliberately.
- Can the primary password be eliminated after initial browser authorization, rather than retained indefinitely in `.env`?
- What is the supported token revocation/logout mechanism and recovery process after compromise?
- What real 780G response shapes, freshness behavior, concurrent-session behavior, and timestamp semantics will be observed after the scheduled November 2026 validation?

## Overall assessment

HIGH legal/account-continuity uncertainty; HIGH confidentiality impact if host/tokens/logs are compromised; HIGH medical-safety impact if stale or transformed data is trusted; MODERATE current attack-surface posture due to good deployment/repository controls but two concrete local confidentiality gaps. Confidence: high for cited code and official documents; medium for community operational history; legal conclusions intentionally left to counsel.
