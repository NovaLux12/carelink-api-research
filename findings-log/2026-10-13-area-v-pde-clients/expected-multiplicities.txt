# expected-multiplicities.txt — the per-identifier multiplicities area V PUBLISHED,
# stated independently of the grouping code that recomputes them. GENERATED, then
# committed as data: it is not hand-typed (this pass published two hand-typed
# numbers that disagreed with its own artefact, so the file that guards against
# that must not itself be typed by hand).
#
# WHY THIS FILE EXISTS. The first version of extract.sh's arithmetic guard compared
# `sum(len(v) for v in groups.values())` against `len(hits)` — but `groups` is built
# by iterating `hits`, so the partition sum IS the size of the set it partitions.
# The assertion was a tautology, could not fire, and FINDINGS.md nevertheless
# described it as stopping a class of error "silently". A check that looks like it
# ran is worse than no check (docs/09 §5): it converts a gap into a green tick.
#
# WHAT THE GUARD NOW CHECKS. extract.sh recomputes every group from the bytes and
# compares it against these stated multiplicities, so it fires when the published
# table and the bundles disagree — which is exactly the defect this pass made twice
# (a hand-written `x5`/`x4` that cancelled; `discover` published as 0 against a
# `cs=12` in the same file).
#
# WHAT IT DOES NOT DO, and that is not a formality: it cannot catch a wrong FIRST
# derivation, because these rows were authored by the same pass from the same
# bundles. This is drift detection between published numbers and bytes, NOT proof
# the published numbers were right the first time. Every row was re-derived
# independently and set-compared before being committed.
#

# Multiplicity only. The case-sensitivity CLASS (cs / ci / partial) is derived by
# the script from the bytes and printed in the section header; it is deliberately
# NOT duplicated here, so this file cannot disagree with the script about it.
